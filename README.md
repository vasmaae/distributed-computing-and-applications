# Лабораторная 8 — параллельная сортировка слиянием

Ветка `lab/08-sort` начинается от первоначального коммита и содержит только библиотеку
`mergesort`, её тесты и бенчмарки. Интеграция с сервисом сотрудников находится
в ветке `lab/08-multithreaded-computing`, которая продолжает лабораторную 7.

Библиотека использует только стандартную библиотеку Go: горутины и `sync.WaitGroup`.
Параметр `threads` задаёт число первоначальных горутин, а не число потоков ОС.
Фактическое исполнение на ядрах ограничивает Go runtime (`GOMAXPROCS`).

## Использование

```sh
go get github.com/vasmaae/distributed-computing-and-applications/mergesort@v0.0.1
```

```go
ids := []int{3, 2, 6, 9, 2, 3, 5, 8, 2, 1, 11}
err := mergesort.Sort(ids, 5, cmp.Compare[int])
// ids: [1 2 2 2 3 3 5 6 8 9 11]
```

Импорты: `cmp` и `github.com/vasmaae/distributed-computing-and-applications/mergesort`.
Функция меняет переданный срез. Компаратор возвращает отрицательное число, ноль
или положительное число по правилам `slices.SortFunc`; он должен допускать
одновременные вызовы из нескольких горутин. Для обратного порядка поменяйте
аргументы сравнения местами. Равные элементы сохраняют исходный порядок.
Неположительное число потоков и отсутствующий компаратор возвращают ошибку до изменения данных.

## Алгоритм

Срез разбивается на `min(threads, len(values))` соседних частей. Каждая часть
сортируется последовательной сортировкой слиянием в своей горутине.
После ожидания всех горутин соседние отсортированные части попарно сливаются
параллельно. Непарная часть переносится на следующий этап.
Число задач на этапах уменьшается с округлением вверх: `5 → 3 → 2 → 1`.
Горутины записывают в непересекающиеся области общего вспомогательного буфера.
Время — `O(n log n)` сравнений, дополнительная память — `O(n)`.
При `threads > n` лишние горутины не создаются; пустой срез обрабатывается сразу.

Для массива из задания после первоначальной сортировки пяти частей:

```text
2,3 | 6,9 | 2,3 | 5,8 | 1,2,11
2,3,6,9 | 2,3,5,8 | 1,2,11
2,2,3,3,5,6,8,9 | 1,2,11
1,2,2,2,3,3,5,6,8,9,11
```

## Проверки и замеры

```sh
cd mergesort
go test -race ./...
go test -run '^$' -bench BenchmarkSort -benchmem -benchtime=200ms -count=3
```

Тесты сравнивают результаты с `slices.SortFunc`, проверяют пример из задания,
пустой срез, повторы, отрицательные числа, прямой и обратный порядок, нечётные
размеры, разные числа потоков, ошибки параметров и сортировку записей.
Бенчмарки используют одинаковые исходные данные для каждого числа потоков;
копирование исходного массива перед итерацией не входит в измерение сортировки.

## Версионирование

Go-модуль расположен в `mergesort/`, поэтому его Git-тег — `mergesort/v0.0.1`,
а версия зависимости в `go.mod` — `v0.0.1`. Локальный `replace` не требуется.

### Результаты замеров

Apple M5 Pro, darwin/arm64, Go 1.27.2, `GOMAXPROCS=18`. Медиана трёх запусков, миллисекунды на сортировку.

| Элементов | 1 горутина | 2 | 3 | 5 | 8 |
|---:|---:|---:|---:|---:|---:|
| 1000 | 0.031 | 0.023 | 0.025 | 0.027 | 0.028 |
| 100000 | 7.315 | 4.027 | 3.012 | 2.254 | 1.936 |
| 1000000 | 86.930 | 47.175 | 34.321 | 24.710 | 18.685 |

На небольших данных запуск и ожидание горутин могут стоить дороже распараллеливания.
На больших данных несколько горутин ускоряют сортировку; рост числа горутин не даёт
линейного ускорения из-за последовательного финального слияния, памяти и планировщика.
Результаты зависят от процессора и нагрузки; эти значения получены без `-race`.
