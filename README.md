# Distributed computing and applications

Лабораторные выполняются последовательно в ветках `lab/XX-<name>`, коммиты — `lab-XX: <description>`.
Реальные настройки хранятся в игнорируемых `<service>/.env`; в Git добавляются только `example.env`.

## Запуск

Скопируйте `example.env` в `.env` в каталогах `database`, `employees`, `reports`, `files`, `storage`, `queue`, `kafka-ui`, `monitoring`.
В `files/.env` и `storage/.env` должны совпадать S3-ключи и имя бакета. Замените демонстрационные пароли.

```sh
docker compose up -d --build
```

Шлюз: `http://localhost:8080`. Swagger: `http://localhost:8080/employees/swagger/index.html`.
Опубликованные порты привязаны к localhost.
Сервисы отчётов, файлов и S3 доступны только внутри Docker-сети.
В ветке №7 для API сначала получите JWT по инструкции ниже и добавляйте `Authorization: Bearer <token>`.
Для сборки Docker используется корень репозитория: `docker build -f employees/Dockerfile .`.

Разделы ниже описывают развитие проекта в соответствующих ветках. Примеры лабораторных 1–6
приведены без авторизации; при выполнении в текущей ветке №7 добавляйте JWT, как показано
в разделе «Лабораторная 7 — JWT и наблюдаемость».

## Лабораторная 1 — основной сервис сотрудников

Ветка: `lab/01-main-service`.

Реализован REST API управления сотрудниками на Go: HTTP-обработчики, бизнес-логика и
репозиторий PostgreSQL через GORM. Схема БД создаётся миграциями tern при запуске приложения.
Сотрудник содержит `id` (UUID), `fio`, `birth_date` и признак увольнения `is_fired`.
Проверяются формат ФИО и дата рождения; возраст сотрудника должен быть не менее 14 лет.

| Метод | Маршрут внутри сервиса | Действие |
|---|---|---|
| `GET` | `/api/v1/employees` | Получить список сотрудников |
| `GET` | `/api/v1/employees/{id}` | Получить сотрудника по UUID |
| `POST` | `/api/v1/employees` | Создать сотрудника |
| `PUT` | `/api/v1/employees/{id}` | Изменить ФИО и дату рождения |
| `DELETE` | `/api/v1/employees/{id}` | Отметить сотрудника уволенным |

Удаление логическое: устанавливается `is_fired=true`, запись остаётся в БД и учитывается
в отчётах. При создании и изменении данные передаются в JSON, дата рождения — в формате RFC 3339.
Неверные данные возвращают 400, отсутствующий сотрудник — 404.

В ветке №1 сервис опубликован напрямую: `http://localhost:8080/api/v1/employees`,
Swagger — `http://localhost:8080/swagger/index.html`. В последующих работах запросы идут
через шлюз с префиксом `/employees`:

```sh
curl http://localhost:8080/employees/api/v1/employees
curl -X POST http://localhost:8080/employees/api/v1/employees \
  -H 'Content-Type: application/json' \
  -d '{"fio":"Иванов Иван Иванович","birth_date":"1995-06-15T00:00:00Z"}'
```

## Лабораторная 2 — сервис отчётов

Ветка: `lab/02-report-service`.

Основной сервис перенесён в каталог `employees`, добавлен отдельный Go-сервис `reports`.
На этом этапе оба сервиса читают общую БД PostgreSQL: reports получает сотрудников напрямую
через свой репозиторий. Отчёт возвращается в JSON и содержит список `employees`, общее число
сотрудников `total` и количество уволенных `is_fired`.

Nginx предоставляет общий внешний адрес и проксирует `/employees/` в основной сервис,
а `/reports/` — в сервис отчётов. В ветке №2 доступны отдельные Swagger-страницы:
`/employees/swagger/index.html` и `/reports/swagger/index.html`.

```sh
curl http://localhost:8080/reports/api/v1/reports/employees-report
```

Этот публичный маршрут относится к ветке №2. Начиная с лабораторной №3 запрос отчёта
выполняется через основной сервис, как показано ниже.

## Лабораторная 3 — HTTP-взаимодействие и единая точка входа

Ветка: `lab/03-gateway`.

Основной сервис получает маршрут формирования отчёта и обращается к reports по HTTP.
В свою очередь, reports запрашивает список сотрудников по HTTP у employees вместо прямого
чтения его БД. Запросы используют контекст и HTTP-таймаут; ошибки зависимого сервиса
преобразуются в HTTP-ошибку ответа основного сервиса (424).

Внешний маршрут `/reports/` убран из Nginx: сервис отчётов доступен внутри Docker-сети,
а клиент работает через основной API и его Swagger. Префикс `/employees/` обрабатывается
шлюзом; сами обработчики Go по-прежнему используют маршруты `/api/v1/...`.

```sh
curl http://localhost:8080/employees/api/v1/reports/employees-report
```

Ответ пока содержит только JSON с сотрудниками и итоговыми счётчиками. Сохранение CSV
и поле `file_id` добавляются в лабораторной №4, очередь доставки — в №5.

## Лабораторная 4 — файловое хранилище

```sh
curl http://localhost:8080/employees/api/v1/reports/employees-report
```

Основной сервис запрашивает отчёт по HTTP. Сервис отчётов получает сотрудников из основного
сервиса, формирует CSV (`id,fio,birth_date,is_fired`) и в ветке №4 передаёт его по HTTP файловому сервису.
Тот сохраняет CSV в S3-совместимый SeaweedFS. Ответ содержит `file_id`, `employees`, `total`, `is_fired`.
Лимит одного CSV — 8 MiB. Для пустого списка сохраняется CSV с заголовком.

В ветке №4 скачивание доступно внутри сети (в №7 этот запрос также требует JWT):

```sh
docker compose exec -T files-1 wget -qO- http://localhost:8080/api/v1/files/FILE_ID
```

Проверка: `python3 scripts/smoke.py`. В каждом Go-модуле: `go test ./...`.

## Лабораторная 5 — очередь

В `lab/05-queue` HTTP-передача CSV заменена Kafka (один узел в режиме KRaft).
`QUEUE_BROKERS` и `QUEUE_TOPIC` в `reports/.env` и `files/.env` должны совпадать;
топик из `queue/.env` автоматически создаётся `kafka-init` при запуске Compose.
Продюсер ожидает подтверждения Kafka (`acks=all`). `file_id` возвращается после записи сообщения,
поэтому до обработки скачивание может вернуть 404. Потребитель фиксирует offset только после записи в S3.
При сбое контейнер перезапускается и повторно читает неподтверждённое сообщение с тем же UUID;
запись по тому же ключу позволяет безопасно повторить доставку.
Повреждённые сообщения пропускаются с записью в лог, чтобы не блокировать партицию.
Лимит CSV — 8 MiB; лимиты Kafka учитывают накладные расходы сообщения.
Данные Kafka сохраняются в Docker volume. Один брокер не обеспечивает отказоустойчивость при потере диска.

## Лабораторная 6 — Future на Go

В проекте на Go роль `CompletableFuture` выполняют goroutine и буферизированный канал результата.
`GetAsync` сразу возвращает канал; основной сервис ожидает CSV через `select`, учитывая отмену запроса
и таймаут 5 секунд. Запрос к файловому сервису использует тот же контекст. Буфер канала позволяет
goroutine завершиться, даже если клиент уже отключился.

Добавьте `FILES_CLIENT_HOST`/`FILES_CLIENT_PORT` из `employees/example.env` в локальный `.env`.
После получения `file_id` скачайте CSV через шлюз:

```sh
curl -OJ http://localhost:8080/employees/api/v1/reports/files/FILE_ID
```

Неизвестный или ещё не обработанный файл возвращает 404, неверный UUID — 400,
сбой файлового сервиса — 502, истечение времени ожидания — 504.

## Лабораторная 7 — JWT и наблюдаемость

В `employees/.env` задайте `AUTH_USERNAME`, `AUTH_PASSWORD`. Во всех трёх сервисах укажите одинаковый
`JWT_SECRET` длиной не менее 32 байт. Значения не включаются в Git и Docker build context.
Пароль локальной учётной записи хранится в `employees/.env`.

```sh
curl http://localhost:8080/employees/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"<AUTH_USERNAME>","password":"<AUTH_PASSWORD>"}'
```

Этот запрос доступен и в Swagger: **auth → POST /auth/login → Try it out**.
Прежний адрес `/employees/auth/login` также работает.
Сохраните `access_token` из ответа в переменную `TOKEN`. Токен действует 15 минут.

```sh
curl -H "Authorization: Bearer $TOKEN" \
  http://localhost:8080/employees/api/v1/reports/employees-report
curl -OJ -H "Authorization: Bearer $TOKEN" \
  http://localhost:8080/employees/api/v1/reports/files/FILE_ID
```

В Swagger нажмите **Authorize** и вставьте `Bearer <access_token>`.
Все бизнес-эндпоинты трёх сервисов проверяют подпись HS256, срок действия, issuer, audience и subject.
Токен передаётся только по внутренним HTTP-запросам; в сообщения Kafka он не включается.
Учётная запись одна, настраивается через env; регистрации, ролей и refresh-токенов нет.

`OTEL_EXPORTER_OTLP_ENDPOINT=http://jaeger:4318` включает экспорт трасс.
OpenTelemetry передаёт W3C `traceparent` через HTTP, Kafka и обращения к S3.
В [Jaeger](http://localhost:16686) выберите `employees-service` и запрос отчёта:
в одной трассе будут основной сервис, отчёты, публикация/обработка очереди и запись S3.
При скачивании создаётся отдельная трасса основного и файлового сервисов.
Jaeger хранит трассы в памяти, поэтому перезапуск очищает их.

[Prometheus](http://localhost:9090/targets) собирает `/metrics` всех трёх сервисов каждые 5 секунд.
Доступны `http_requests_total`, `http_request_duration_seconds` и метрики Go/process.
Метки используют шаблоны маршрутов, поэтому UUID не создают новые временные ряды.
Метрики не публикуются через шлюз; UI Prometheus и Jaeger доступны только на localhost.

### Kafka UI и Grafana

| Страница | Что показать |
|---|---|
| [Swagger](http://localhost:8080/employees/swagger/index.html) | JWT, CRUD сотрудников, отчёт и скачивание CSV |
| [Kafka UI](http://localhost:8081) | Кластер `local`, топик `reports.files`, сообщения, группа `files-service` и lag |
| [Grafana — Services overview](http://localhost:3000/d/services/services-overview) | Состояние и метрики трёх сервисов |
| [Prometheus Targets](http://localhost:9090/targets) | Проверка, что все сервисы имеют статус UP |
| [Jaeger](http://localhost:16686/search) | Трасса HTTP → Kafka → S3 |
| [Kibana — Discover](http://localhost:5601/app/discover) | Поиск логов всех сервисов по `service`, `level`, `trace_id`, `file_id` |

Kafka UI — [Kafbat UI](https://ui.docs.kafbat.io/overview/getting-started), заранее подключён к трём Kafka-узлам.
Вход в Grafana — логин и пароль `GF_SECURITY_ADMIN_USER` / `GF_SECURITY_ADMIN_PASSWORD`
из локального `monitoring/.env`. Не используйте пароль приложения вместо пароля Grafana.
При первом запуске Grafana создаёт учётную запись; изменение `.env` после этого само по себе пароль не меняет.

Prometheus и дашборд подключаются через [file provisioning Grafana](https://grafana.com/docs/grafana/latest/administration/provisioning/).
Ручной импорт не нужен. В дашборде шесть панелей: доступность сервисов, число запросов за выбранный
интервал, запросы в секунду, p95 времени ответа, ошибки HTTP 4xx/5xx и память RSS.
Сверху можно выбрать сервис, период и перейти в остальные инструменты демонстрации.
Обновление — каждые 5 секунд. p95 и частота запросов отражают интервалы с реальным трафиком.
Создайте несколько отчётов и скачайте CSV через Swagger, чтобы показать изменения на графиках.

Дашборд хранится в `monitoring/grafana/dashboards/services.json`, настройки источника и загрузки —
в `monitoring/grafana/provisioning`. Правки дашборда делаются в JSON. Данные Grafana сохраняются
в volume `grafana_data`; пароли — только в игнорируемом `.env`. Kafka UI и Grafana доступны на localhost.

### Логирование

```sh
docker compose logs -f employees-1 employees-2 reports-1 reports-2 files-1 files-2
python3 scripts/smoke.py
```

Все три Go-сервиса (`employees-service`, `reports-service`, `files-service`) пишут в stdout
по одной JSON-строке на событие. Общий `common/telemetry.InitLogging` вызывается до загрузки
конфигурации: запуск и ошибки настроек тоже имеют поля `time`, `level`, `msg`, `service`.
Логи из контекста HTTP/Kafka автоматически получают `trace_id` и `span_id`.
HTTP middleware добавляет `method`, шаблон `route`, `status`, `duration_ms`: 2xx/3xx — INFO,
4xx — WARN, 5xx — ERROR. `/metrics` не засоряет логи. Паника обработчика записывается
как ERROR с `error` и `stack`, затем клиент получает 500.

Ошибки БД логируются на границе HTTP с контекстом трассы. Стандартный вывод GORM отключён,
чтобы SQL с ФИО и другими значениями не попадал в лог. Прикладные ошибки, ошибки записи ответа
и HTTP-сервера также используют JSON. Продюсер Kafka пишет `published queued report`,
потребитель — `saved queued report`; обе записи содержат `file_id` и общий `trace_id`.
Повреждённое сообщение — WARN с топиком, партицией и offset, сбой сохранения — ERROR.
Пароли, JWT, заголовки авторизации и тела запросов не записываются.

Цепочка сбора: **stdout/stderr → Docker json-file → Filebeat → Logstash → Elasticsearch → Kibana**.
[Filebeat autodiscover](https://www.elastic.co/docs/reference/beats/filebeat/configuration-autodiscover)
выбирает контейнеры с меткой `distributed.logs=json`; в Compose она включена у трёх Go-сервисов.
Logstash разбирает JSON, преобразует `time` в `@timestamp`, `msg` в `message` и индексирует
события в `app-logs-YYYY.MM.dd`. Неожиданный текстовый вывод сохраняется с `_jsonparsefailure`
и уровнем ERROR. Типы полей заданы шаблоном: `trace_id`, `service`, `level` и `file_id` доступны
для точного поиска и группировок, `message` и `error` — для полнотекстового поиска.

В [Kibana Discover](http://localhost:5601/app/discover) представление **Application logs**
(`app-logs-*`) создаётся автоматически через `logging-setup` и выбирается по умолчанию.
После запроса отчёта откройте Discover, выберите время **Last 15 minutes**, нажмите Refresh.
Примеры запросов KQL в строке поиска:

```text
service: "employees-service"
level: "ERROR"
status >= 400
trace_id: "<trace_id из лога или smoke.py>"
file_id: "<file_id отчёта>"
service: "files-service" and message: "saved queued report"
```

Колонки `service`, `level`, `message`, `status`, `trace_id` настраиваются автоматически.
По одному `trace_id` видны HTTP-вызовы, публикация в Kafka и сохранение CSV;
этот же ID можно открыть в Jaeger: `http://localhost:16686/trace/<trace_id>`.
Конфигурация стека лежит в `logging/`, готовые настройки индекса и представления — в `logging/setup/`.
Elasticsearch API для проверки — [localhost:9200](http://localhost:9200).

Индексы сохраняются в volume `elasticsearch_data`, позиции чтения и дисковые очереди —
в `filebeat_data` и `logstash_data`. У Filebeat и Logstash очереди по 256 MiB с повторной отправкой
при недоступности Elasticsearch. Доставка допускает повторы после аварийного завершения.
Docker ротирует исходные логи (3 файла по 10 MiB на сервис); длительный простой сборщика
может привести к утрате ещё не прочитанных записей после ротации. Индексы автоматически
не удаляются: для длительной эксплуатации нужна политика хранения и контроль свободного места.
`docker compose down` сохраняет историю; **`docker compose down -v` удаляет volumes вместе с данными**.

ELK запускается вместе со стендом через `docker compose up -d --build`.
Первый запуск требует загрузки крупных образов и может занять несколько минут;
Docker Desktop рекомендуется выделить не менее 8 GB памяти для всего стенда.
Это локальный одновузловой ELK без TLS и отдельной авторизации, порты 5601 и 9200
привязаны к localhost. Для удалённого доступа нужно включить безопасность Elastic.
Filebeat использует доступ к Docker API и каталогу логов; стенд рассчитан на доверенную локальную машину.

`smoke.py` читает учётные данные из локальных `employees/.env` и `monitoring/.env`, проверяет JWT,
CSV, цели Prometheus, трассу HTTP → Kafka → S3, чтение топика через Kafka UI и запросы всех
шести панелей Grafana к Prometheus, индексирование JSON-логов трёх сервисов с общим `trace_id`
и настройку Kibana; секреты не печатает.
Стенд использует HTTP и предназначен для локальной демонстрации; внешний доступ требует TLS.

Проверки модулей:

```sh
for service in common employees reports files; do
  (cd "$service" && go test -race ./...)
done
```

Основной Compose сохраняет порт PostgreSQL 5432 для локальной разработки.
Если он занят другим приложением, освободите его или используйте временный Compose override,
не меняя адрес БД внутри Docker-сети (`postgres:5432`).

## Несколько инстансов: Docker DNS и Nginx

По умолчанию запущено по два инстанса каждого Go-сервиса. Внутри сети адреса
`http://employees-service`, `http://reports-service`, `http://files-service` ведут на Nginx
(порт 80), который распределяет HTTP-запросы round-robin. Приложения слушают 8080.
Внешний адрес Swagger остаётся прежним; публичный listener Nginx отделён от внутреннего.
Метрики доступны Prometheus напрямую и не открываются через gateway.

Общие настройки инстансов объявлены в шаблонах Compose. Чтобы добавить ещё один,
добавьте в `services` строку `employees-3: *employees-instance` и выполните
`docker compose up -d --build employees-3`. Для других типов используются
`*reports-instance` и `*files-instance`. Шаблон включает общий backend-алиас;
Nginx обновляет список адресов через Docker DNS каждые 5 секунд без reload.
Также можно масштабировать один блок: `docker compose up -d --scale employees-1=3`.
После добавления нового типа приложения ему потребуется отдельный upstream и логический адрес.

Из `employees/example.env` и `reports/example.env` перенесите порты HTTP-клиентов `80`
в локальные `.env`; секреты сохраняются в прежних игнорируемых файлах.
Первый переход со старых имён контейнеров: `docker compose up -d --build --remove-orphans`.
Общая БД, S3 и одинаковые JWT-настройки позволяют обслуживать запрос на любом инстансе.
Заголовок `X-Service-Instance`, поле JSON `instance_id` и атрибут трассы
`service.instance.id` показывают конкретный контейнер. Prometheus использует DNS discovery
для каждого backend, Grafana различает экземпляры в панелях доступности и памяти.

`/healthz` проверяет запуск HTTP-сервера и не создаёт логов/трасс. Docker DNS не фильтрует
`unhealthy`; Nginx использует пассивное исключение сбоев на 5 секунд. Во время обновления DNS
или отказа возможен ответ 502/504. Автоматические повторы отключены, поскольку даже GET отчёта
публикует сообщение Kafka. После удаления инстанса дождитесь обновления DNS.
Nginx, PostgreSQL и управляющий узел S3 пока остаются отдельными точками отказа.

Проверка балансировки, добавления и остановки инстанса: `python3 scripts/check_instances.py`.
Скрипт удаляет созданный тестовый контейнер и восстанавливает остановленную реплику.

## Кластер Kafka

`kafka-1`, `kafka-2`, `kafka-3` — три узла Kafka 4.1 в совмещённом режиме broker/controller.
У каждого свой `node.id`, объявленный адрес и volume. `kafka_data` сохранён за узлом 1,
два других используют `kafka_2_data` и `kafka_3_data`. Клиенты и Kafka UI получают все три
bootstrap-адреса из своих `.env` (сверьте с `example.env`). HTTP-балансировщик здесь не участвует:
Kafka-клиент получает метаданные и соединяется с лидером нужной партиции напрямую.

При чистом запуске узел 1 создаёт динамический KRaft-кворум, два других подключаются как
наблюдатели. `kafka-init` добавляет их в голосующий состав и настраивает топики:
`reports.files` имеет 3 партиции, replication factor 3 и min ISR 2. Продюсер сохраняет `acks=all`.
Также реплицируются существующие партиции и служебные топики, включая `__consumer_offsets`;
повторный запуск инициализации допустим. Две реплики `files-service` делят три партиции
одной consumer group, поэтому обе могут обрабатывать сообщения параллельно.

Для перехода с прежнего одиночного узла, пока его старый контейнер ещё работает, сначала
обновите формат кворума официальной командой Kafka 4.1:

```sh
docker exec distributed-computing-and-applications-kafka-1 \
  /opt/kafka/bin/kafka-features.sh --bootstrap-server localhost:9092 upgrade --feature kraft.version=1
```

Перед переходом остановите producers/consumers и сохраните резервную копию `kafka_data`.
Затем остановите старый Kafka-контейнер, перенесите настройки из `queue/example.env`,
`reports/example.env`, `files/example.env`, `kafka-ui/example.env` в локальные `.env` и запустите
`docker compose up -d --build --remove-orphans`. Не удаляйте исходный volume и не форматируйте
его повторно. Имя старого контейнера в команде выше приведено для стандартного имени проекта.
В текущем стенде переход уже выполнен с сохранением истории.

Проверка: `python3 scripts/check_kafka.py` проверяет состав кворума, реплики и ISR,
останавливает `kafka-1`, создаёт и скачивает отчёт через оставшиеся узлы, затем восстанавливает
узел и дожидается его возвращения в ISR. После отказа возможна короткая пауза выборов лидера.
Для работы кворума нужны 2 из 3 контроллеров; для записи нужны минимум 2 синхронные реплики.
Схема рассчитана на отказ одного Kafka-узла, а не двух одновременно.

## Распределённое хранение S3

SeaweedFS использует три volume server: встроенный в `seaweedfs` и отдельные
`seaweedfs-volume-2`, `seaweedfs-volume-3`. Каждый хранит данные в своём Docker volume;
первые данные сохранены в прежнем `seaweedfs_data`, каталог томов — `/data/data`.
Адрес S3 для приложений остаётся `http://seaweedfs:8333`, ключи — в локальных `.env`.

Политика [`001`](https://github.com/seaweedfs/seaweedfs/wiki/Replication) означает
две копии на разных volume server в одном rack. Подтверждение записи требует обеих копий.
Master и filer применяют её к новым данным. `seaweedfs-init` также меняет размещение
существующих томов, копирует их содержимое и балансирует тома между узлами; затем проверяет
наличие двух копий. `files-service` запускается после успешной инициализации.
При выделении новых томов filer запрашивает 6 физических томов: 3 логических × 2 копии.
При одинаковом размере дисков полезная ёмкость составляет примерно половину суммарной.
Новые серверы регистрируются у master сами; для расширения добавьте блок по образцу
`seaweedfs-volume-3` с уникальным `-ip` и отдельным volume. Переместить уже созданные тома
на новый сервер можно повторным запуском `seaweedfs-init`.

Перед миграцией существующего стенда остановите `reports-*` и `files-*`, остановите
`seaweedfs` и сохраните резервную копию **всего** `seaweedfs_data`, включая filer metadata.
После `docker compose up -d` и успешного завершения `seaweedfs-init` возобновите приложения.
В текущем стенде миграция выполнена; контрольный прежний CSV проверен по SHA-256.
Проверка `python3 scripts/check_storage.py` проверяет физические копии, останавливает
volume server, содержащий выбранный CSV, читает CSV с оставшейся копии, создаёт новый отчёт
и восстанавливает сервер.

Остановка одного дополнительного volume server оставляет данные доступными со второй копии;
для новых записей нужны два доступных сервера. Возможна пауза обнаружения отказа.
При постоянной потере диска замените его и запустите `docker compose run --rm seaweedfs-init`
для восстановления недостающих копий. Инициализация не удаляет лишние копии автоматически:
если они появились после восстановления старого диска, проверьте размещение через `weed shell`.
Master, filer и S3 gateway по-прежнему находятся в `seaweedfs`: его отказ прерывает доступ
к S3. Все контейнеры работают на одном компьютере; это демонстрация распределения процессов
и данных, а не защита от отказа самого компьютера. Лабораторная №8 не менялась.

## Transactional outbox для CSV-отчётов

`reports-service` использует отдельную БД `reports` на том же PostgreSQL (`postgres:5432`).
`database/init/01-create-reports-database.sql` создаёт БД при первом запуске PostgreSQL.
Для уже существующего volume тот же идемпотентный SQL выполняет сервис `postgres-init`;
исходная БД сотрудников и её данные сохраняются. Таблицы создают встроенные миграции
`reports/internal/migrations`, с блокировкой конкурентного запуска через tern.

Сверьте локальный `reports/.env` с `reports/example.env`: `DATABASE_DATABASE=reports`,
адрес `postgres`, пользователь и пароль — из `database/.env`. Учётные данные остаются
в игнорируемых `.env`; в SQL и Compose секретов нет. Для локального запуска Go-сервиса
вне Docker используйте `DATABASE_HOST=localhost`. Запуск: `docker compose up -d --build`.

Путь записи:

1. Сервис получает сотрудников, формирует CSV и назначает `file_id`.
2. Одной транзакцией PostgreSQL вставляет метаданные отчёта в `reports` и неизменяемый CSV
   с trace context в `report_outbox`. При ошибке любой вставки откатываются обе.
3. После commit API возвращает прежний ответ HTTP 200 с `file_id` и данными отчёта.
   Это подтверждение формирования отчёта и надёжной постановки CSV на доставку.
4. Worker каждого инстанса `reports` выбирает готовую задачу через
   `FOR UPDATE SKIP LOCKED`, публикует CSV в Kafka с `acks=all` и только после подтверждения
   помечает задачу отправленной. При отказе Kafka API продолжает сохранять новые задания,
   пока доступны PostgreSQL и сервис сотрудников.
5. `files-service` сохраняет CSV в S3 под ключом `file_id` и подтверждает Kafka offset
   только после успешной записи. До этого скачивание может возвращать 404.

Запуск `reports` и gateway не требует готовности Kafka/`files`; HTTP API можно поднять
через `docker compose up -d nginx`, даже если Kafka временно выключена. Скачивание файлов
требует доступности `files` и S3.

У отправленной задачи `published_at` заполнен, а `csv` освобождается (`NULL`), чтобы не
хранить вторую долговременную копию содержимого в PostgreSQL. Записи отчётов, отметки отправки
и счётчик зафиксированных попыток сохраняются. `published_at` означает подтверждение Kafka, а не готовность объекта
в S3; готовность проверяется скачиванием по прежнему URL.
У ожидающей задачи сохранены CSV, `attempts`, `available_at`, `last_error` и trace context.
После ошибки интервал повторов растёт с 1 до 60 секунд; после перезапуска задачи остаются в БД.
Блокировка строки удерживается во время ограниченной по времени публикации: один worker
на инстанс, максимум 4 соединения с БД на инстанс. Соседние workers пропускают занятую строку.

Гарантия доставки — **at least once**. Если Kafka приняла сообщение, а процесс завершился
до commit отметки отправки, сообщение уйдёт повторно с тем же UUID и теми же байтами CSV.
Повторный `PutObject` заменяет содержимое того же S3-ключа, не создавая новый логический файл.
Это локальная транзакция PostgreSQL и идемпотентная доставка, а не общая ACID-транзакция
PostgreSQL/Kafka/S3. Повтор самого HTTP-запроса формирует новый отчёт с новым `file_id`.
Задачи не переводятся в окончательный `failed` после заданного числа попыток: ошибки нужно
исправить, после чего worker продолжит доставку. История строк автоматически не удаляется;
при длительном использовании нужна политика хранения, при долгом отказе Kafka — контроль
размера очереди в PostgreSQL и retention Kafka для уже опубликованных задач.

Логи постановки, повторов и публикации содержат `file_id`, конкретный `instance_id` и
исходный `trace_id`. Контекст проходит через PostgreSQL и Kafka до `files-service`;
Jaeger показывает `outbox deliver` и Kafka publish/process в исходной трассе.

Проверки:

- `python3 scripts/check_outbox.py`: выключает все Kafka-узлы, поднимает gateway без них,
  создаёт отчёты, перезапускает
  PostgreSQL и оба `reports`, восстанавливает Kafka, проверяет CSV и повторную доставку
  по тому же ключу (включая повторный лог сохранения в ELK). Восстанавливает остановленные сервисы.
- `TEST_DATABASE_DSN='postgres://USER:PASSWORD@localhost:5432/reports?sslmode=disable' go test -race ./internal/outbox`
  из каталога `reports`: проверяет rollback, неизменность payload/trace context при повторе,
  сбой SQL после успешной публикации и параллельные workers. Каждый тест создаёт и удаляет
  свою временную схему; без `TEST_DATABASE_DSN` интеграционные проверки пропускаются.
- `python3 scripts/smoke.py`: прежние JWT, CSV, Future, метрики, трассы и JSON-логи.

Для демонстрации очереди без содержимого CSV и секретов:

```sh
docker compose exec postgres sh -c 'psql -U "$POSTGRES_USER" -d reports -c "SELECT file_id, attempts, available_at, published_at, last_error FROM report_outbox ORDER BY available_at DESC LIMIT 10"'
```

### Запрос через gateway

После входа из лабораторной 7 используйте `TOKEN`:

```sh
curl http://localhost:8080/employees/api/v1/employees/sorted \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"sort_by":"birth_date","order":"asc","threads":5}'
```

Это `POST` с тремя обязательными полями:

| Поле | Допустимые значения |
|---|---|
| `sort_by` | `id`, `birth_date`, `fio` |
| `order` | `asc`, `desc` |
| `threads` | Целое число от 1 до 256 |

Неверные или отсутствующие значения, неизвестные поля, несколько JSON-значений
в одном теле и тело больше 4 KiB возвращают `400`. Без JWT запрос возвращает `401`.
Ограничение 256 защищает сервис от чрезмерного числа горутин в одном запросе.
Если сотрудников меньше, число первоначальных горутин уменьшается до их количества.

Пример структуры ответа для пустого списка:

```json
{
  "employees": [],
  "sort_duration_ms": 0.000125
}
```

`employees` содержит полные записи в прежнем формате: `id`, `fio`, `birth_date`, `is_fired`.
Время возвращается в миллисекундах с дробной частью. Измеряется подготовка ключей
сравнения ФИО и вызов сортировки, включая выделение буфера, запуск и ожидание горутин.
Чтение БД, преобразование DTO и сериализация JSON в это время не входят.
Исходные данные в БД не изменяются. Обычный `GET /employees` продолжает возвращать
JSON-массив, поэтому сервис отчётов использует прежний контракт.

Правила сравнения:

- `id`: сравнение всех 16 байт UUID в сетевом порядке через `UUID.Compare`.
  Сотрудники создаются с UUID v7: сначала сравнивается временная часть,
  при совпадении миллисекунды — оставшиеся биты UUID. Преобразование в число
  или выделение одного timestamp не требуется.
- `birth_date`: сравнение значений `time.Time`; `asc` идёт от ранней даты к поздней.
- `fio`: сравнение строк в нижнем регистре, с одиночными пробелами и заменой `ё` на `е`.
  Ключи готовятся один раз до параллельного сравнения. Данные в ответе не нормализуются.
  Это упрощённое алфавитное сравнение, без отдельной языковой колляции.

Сравнивается только выбранное поле. Дополнительного сравнения по ID при равных
датах или ФИО нет. Сортировка слиянием сохраняет взаимный порядок равных элементов,
полученный из БД; сам порядок чтения БД между запросами не фиксируется.

### Алгоритм и проверка числа потоков

Библиотека принимает срез, число горутин и функцию сравнения. Первоначальные части
сортируются слиянием параллельно, затем соседние части попарно объединяются.
Для пяти первоначальных частей число задач по этапам: `5 → 3 → 2 → 1`.
Синхронизация — `sync.WaitGroup`, горутины записывают в непересекающиеся области
буфера. Сторонних зависимостей у библиотеки нет. Параметр `threads` задаёт горутины;
число одновременно исполняемых на ядрах задач ограничивает Go runtime (`GOMAXPROCS`).

Для воспроизведения замеров в ветке библиотеки:

```sh
git switch lab/08-sort
cd mergesort
go test -race ./...
go test -run '^$' -bench BenchmarkSort -benchmem -benchtime=200ms -count=3
```

Результаты на Apple M5 Pro, darwin/arm64, Go 1.27.2, `GOMAXPROCS=18`.
Медиана трёх запусков, миллисекунды на сортировку одинаковых исходных массивов;
копирование исходного массива перед каждой итерацией исключено из измерения.

| Элементов | 1 горутина | 2 | 3 | 5 | 8 |
|---:|---:|---:|---:|---:|---:|
| 1 000 | 0.031 | 0.023 | 0.025 | 0.027 | 0.028 |
| 100 000 | 7.315 | 4.027 | 3.012 | 2.254 | 1.936 |
| 1 000 000 | 86.930 | 47.175 | 34.321 | 24.710 | 18.685 |

На больших данных восемь горутин дали ускорение примерно в 4.65 раза относительно
одной. На маленьком массиве лучший результат дали две горутины; дальнейшее увеличение
числа задач увеличило накладные расходы. Ускорение не линейное: финальное слияние
последовательное, также влияют память, планировщик и нагрузка на процессор.

### Проверка интеграции

В работающем стеке после сборки нового образа:

```sh
python3 scripts/check_sort.py
```

Скрипт читает имеющихся сотрудников без изменения данных, проверяет JWT, все три

параметры и прежний формат обычного GET. Печатает время каждого запроса.
Для содержательной проверки порядка заранее добавьте сотрудников с разными ФИО и датами.

Для проверки только сортировки достаточно PostgreSQL, двух инстансов employees и gateway:


Тесты обработчика проверяют JSON, маршрут, JWT, полный ответ с дробным временем
и отсутствие внутренних сведений в ошибке `500`.

```sh
cd employees
go test -race ./...
```
